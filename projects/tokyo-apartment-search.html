Tokyo Apartment Search

A rental aggregator built for my own move to Tokyo, and a long lesson in why production scraping is an engineering discipline.

Period
Apr–Jul 2026
For
My own move to Tokyo
Scraping
Playwright + Firecrawl fallback
Stack
FastAPI, Celery, Postgres, Next.js

The whatFour portals, one search

A web app that searches Tokyo rentals across Suumo, LIFULL HOME'S, Chintai and e-housing.jp at once. You set the ward, rent range, layout, size and walk time to the station. The backend queues a Celery job, scrapes all four sources concurrently, filters and de-duplicates the results, and stores them in Postgres for a sortable table you can export to CSV.

It then adds what the portals won't let you filter on. For the cheapest matches it opens each detail page to read motorcycle and bicycle parking, whether foreigners are accepted, and whether the building meets the post-1981 earthquake standard (新耐震). Every listing also gets an offline commute estimate to Tokyo Station and Shinjuku.

The whyRenting in Tokyo from abroad

Japan's rental market is hard to navigate from Singapore. Listings are split across competing portals, most of them Japanese-only, and their filters don't line up. The same flat can appear on three sites at slightly different prices.

My criteria were specific: a 1LDK for ¥100,000–120,000, ten minutes' walk from a station, under 40 minutes to Shinjuku, good access to Tokyo Station for the Shinkansen north, and somewhere to park a motorcycle. No portal can filter on all of that. Building the tool also meant I learned the market: by the time it ran, I knew the Koenji and Shin-Koenji corridor was the answer.

How it was builtLive first, Firecrawl when blocked

Each portal has its own HTML, pagination and stance on scrapers. Early on, repeated test runs against Suumo from a Docker container earned a temporary IP block. The code was right; the behaviour wasn't. You can't brute-force scraper development against a live site.

The fix became the architecture. Every scraper now fetches through one shared fetch_page(): try the live site with Playwright first, check the page with a per-site is_blocked() test, and only if it's blocked fall back to Firecrawl's scrape() API, which handles rendering and proxies as a service. Redis remembers which sites are blocking so the next run goes straight to the fallback. Firecrawl costs money per request, so it only runs when it has to.

Around that: FastAPI for the API, Celery and Redis so a 45-second scrape doesn't hold up the page, Alembic migrations so a new column no longer means wiping the database, and a typed listing contract so no scraper can emit a malformed record. The parsers take saved HTML, which is what lets the tests run offline.

What I learnedFour lessons

  1. Scraping is a maintenance contract, not a one-time build.Portals change their markup without notice. Putting block detection and fallback in one shared function meant fixing it once instead of in four copies, and the per-site check turns a silent empty result into a visible block.

  2. Use a managed API as the fallback, not the default.Firecrawl removes the browser, proxy and anti-bot work, but charges per page. Live-first with a Firecrawl fallback gets most of the reliability for a fraction of the cost.

  3. Measure a clever feature before you keep it.I built a cross-source dedup that matched on station, rent, size and floor. On a real run it merged none of the duplicates it was meant to catch and wrongly collapsed 43 different flats. I removed it, and the same search went from 76 to 98 listings. Real cross-language dedup will need coordinates.

  4. The value is in what the portals don't filter.Rent and size are easy. Parking, earthquake standard and commute are what decide a flat, and they live on detail pages. It also showed which source to trust: Chintai's detail pages state motorcycle parking, while Suumo's usually only mention car parking.
