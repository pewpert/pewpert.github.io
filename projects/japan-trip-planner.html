Motorbike Route Planner

Idea to working MVP in a weekend with Claude Code, then a second pass months later to make it hold up on a phone, in the rain.

Period
Mar–Jul 2026
For
Riders touring rural Japan
AI partner
Claude Code
Stack
Next.js 15, TypeScript, Claude API

The whatA trip planner that knows about fuel gaps

A web app for planning multi-day motorcycle trips through rural Japan. It combines Google Maps routing with Claude-written itineraries: plot a route, drag the waypoints, and get a day-by-day plan built around biker-friendly stops, scenic roads and practical logistics.

It suggests a rest stop roughly every two hours, estimates fuel, tolls and accommodation for the whole trip, and ships with four curated routes: Nikko Ridge, Izu Peninsula, the Japanese Alps and Kyushu's Aso Caldera. Since July it also shows an Open-Meteo weather strip along the route, and the map collapses behind a toggle on mobile so the itinerary stays readable.

The whyGeneric planners don't ride

A motorcycle trip through rural Japan has more moving parts than a normal itinerary: road surfaces, long gaps between fuel stops on mountain passes, guesthouses that welcome bikers, seasonal closures. Ask an AI for recommendations without real route data and you get generic advice.

So the app passes Claude the actual route geometry and a curated biker POI dataset, and asks it to reason about that. The suggestions come back spatially coherent instead of merely on-topic.

How it was builtTwo very different passes

March: the weekend sprint. I built the first version with Claude Code in a single weekend, from a rough idea to a working Next.js app with TypeScript, Google Maps and live Claude API calls. I described features in plain English and Claude Code scaffolded components, wired the APIs and suggested patterns I wouldn't have known to use. By the end it had a POI layer, cost ranges, an hourly schedule, a day view and a print-friendly export.

Shipping that fast left real questions. Without deep TypeScript or Next.js knowledge, I couldn't fully audit what was generated. I trusted the output, and I knew how much I was trusting.

June–July: the second pass. I came back with a written improvement brief before touching any code. That pass added the weather strip, whole-trip costs, the mobile map toggle and clearer error messages. It also cut route requests down to a single Directions call per trip, and replaced the look with a Japanese travel-journal design.

What I learnedThree lessons

  1. AI coding is fast, but the time comes back later.Claude Code got me to a working app in two days. The time I saved writing code, I owed back in understanding it when I returned in June. Shipping responsibly means being able to read and audit what was generated.

  2. Grounding the model in real data raises the ceiling.Claude with route geometry and a curated POI dataset produced recommendations a rider could use. The same prompts without that context produced plausible-sounding stops in the wrong places. The context is the product.

  3. Write the brief before you ask for the change.The second pass went far better than the first because I wrote down what was wrong and what "done" looked like before starting. A clear brief is as useful to an AI pair as it is to a human engineer, and it's the same skill I use with clients.
